5. **Проверили красный сценарий и починку:** намеренно сломали тест (`sum(2, 3) === 6`), увидели, что `test_app` упал (`Failed`), а `build_app` пропустился (`Skipped`). Вернули `5` и получили повторный зелёный конвейер.
    

### 2. Использованные команды

- **Локальная проверка проекта:**
    
    - `node --version` — проверка версии Node.js.
        
    - `npm test` — запуск модульных тестов (`node test.js`).
        
    - `npm run build` — создание папки `dist/` и копирование туда файлов приложения.
        
    - `find dist -maxdepth 1 -type f -print` — проверка содержимого `dist/`.
        
- **Работа с Git и GitHub:**
    
    - `git init` / `git branch -M main` — инициализация репозитория и переименование ветки в `main`.
        
    - `git remote add origin [https://github.com/nekootrap/devops-lab5.git](https://github.com/nekootrap/devops-lab5.git)` — привязка удалённого репозитория.
        
    - `git add .` / `git commit -m "..."` / `git push -u origin main` — фиксация и отправка изменений.
        
    - `git log --oneline` — просмотр краткой истории коммитов.
        
- **Изменение теста для проверки реакции CI:**
    
    - `sed -i 's/sum(2, 3), 5/sum(2, 3), 6/' test.js` — намеренная поломка теста (и обратная замена для исправления).
        

### 3. Основные определения и понятия

- **Continuous Integration (CI)** — практика разработки, при которой изменения регулярно отправляются в общий репозиторий, а каждый новый коммит автоматически проверяется сборкой и тестами по единым правилам.
    
- **Pipeline (конвейер)** — полный автоматический процесс проверки конкретного коммита.
    
- **Stage (этап)** — логическая фаза конвейера, определяющая порядок выполнения (`test`, затем `build`).
    
- **Job (задача)** — конкретная изолированная задача внутри конвейера, которую выполняет раннер (`test_app`, `build_app`).
    
- **Runner (исполнитель)** — сервер-агент, который получает job, разворачивает чистую среду (Node.js 20), выполняет команды и возвращает логи, статусы и артефакты.
    
- **Artifact (артефакт)** — готовый результат сборки (`dist/`), сохранённый сервером CI после успешного job и доступный для скачивания.
    
- **Статусы выполнения:**
    
    - `passed` / `Success` — команды завершились успешно (`exit code 0`).
        
    - `failed` — команда завершилась с ошибкой (`exit code != 0`), конвейер остановлен.
        
    - `skipped` — задача пропущена (например, `build_app` не запускается при падении `test_app`).
        
    - `pending` — задача ждёт свободный Runner.
        

### 4. Краткие ответы на контрольные вопросы

1. **Что такое Continuous Integration?** Автоматическая проверка каждого коммита в репозитории (тестирование и сборка) для раннего обнаружения ошибок.
    
2. **Что такое pipeline, stage и job?** Pipeline — весь процесс проверки коммита; stage — логический этап (`test`, `build`); job — конкретная задача внутри этапа, которую запускает Runner.
    
3. **Что делает Runner?** Получает job, поднимает окружение, выполняет команды из сценария и возвращает в систему статусы, логи и артефакты.
    
4. **Где хранится описание pipeline?** В YAML-файле в самом репозитории: `.gitlab-ci.yml` (в GitLab) или `.github/workflows/ci.yml` (в GitHub Actions).
    
5. **Что означает `image: node:20-alpine`?** Указывает раннеру запускать задачи в Docker-контейнере на базе Alpine Linux с установленным Node.js 20 (в GitHub Actions мы использовали `runs-on: ubuntu-latest` + `actions/setup-node@v4` с `node-version: "20"`).
    
6. **Почему `test` и `build` оформлены отдельными jobs?** Чтобы отделить проверку кода от упаковки, сразу видеть этап возникновения ошибки и не тратить ресурсы на сборку при провале тестов.
    
7. **Что означает `exit code 0`?** Консольная команда или тестовый скрипт завершились штатно и без ошибок.
    
8. **Почему ненулевой `exit code` делает job красным?** Код возврата `!= 0` (например, `1` при ошибке `assert`) сигнализирует об аварийном завершении команды, поэтому Runner прерывает шаг и ставит статус `failed`.
    
9. **Что такое artifact и чем он отличается от исходного кода в Git?** Артефакт — это сгенерированный результат сборки (`dist/`), который временно хранится на сервере CI, а не фиксируется в истории коммитов Git.
    
10. **Что произойдёт с `build` job, если `test` stage завершился ошибкой?** Сборка не запустится и получит статус `skipped` (в GitHub Actions это обеспечивается связкой `needs: test_app`), а дефектный артефакт не создастся.
    
11. **Почему CI должен запускаться после изменения в репозитории?** Для быстрой обратной связи (fast feedback) — ошибка выявляется сразу после коммита, до публикации сборки.
    
12. **Чем локальный `npm test` отличается от запуска теста в CI?** Локальный запуск зависит от настроек и пакетов на ПК разработчика, а CI всегда запускает тесты в чистом, изолированном и воспроизводимом окружении.
    
13. **Что такое переменная `$CI_COMMIT_SHORT_SHA`?** Встроенная переменная среды с коротким хэшем текущего коммита для уникального именования артефакта (в GitHub Actions аналог — `${{ github.sha }}`).
    
14. **Где смотреть подробную причину `failed` job?** В журнале выполнения (Job Log) упавшей задачи в веб-интерфейсе CI.
    
15. **Почему намеренно сломанный тест полезен для проверки pipeline?** Он доказывает, что конвейер реально контролирует качество кода, переходит в `failed` при ошибке и блокирует сборку артефакта.
