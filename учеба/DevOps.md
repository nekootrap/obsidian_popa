### 3. Основные определения и понятия

- **Continuous Integration (CI)** — практика разработки, при которой изменения регулярно отправляются в общий репозиторий, а каждый новый коммит автоматически проверяется сборкой и тестами по единым правилам.
    
- **Pipeline (конвейер)** — полный автоматический процесс проверки конкретного коммита.
    
- **Stage (этап)** — логическая фаза конвейера, определяющая порядок выполнения (`test`, затем `build`).
    
- **Job (задача)** — конкретная изолированная задача внутри конвейера, которую выполняет раннер (`test_app`, `build_app`).
    
- **Runner (исполнитель)** — сервер-агент, который получает job, разворачивает чистую среду (Node.js 20), выполняет команды и возвращает логи, статусы и артефакты.
    
- **Artifact (артефакт)** — готовый результат сборки (`dist/`), сохранённый сервером CI после успешного job и доступный для скачивания.
    
- **Статусы выполнения:**
    
    - `passed` / `Success` — команды завершились успешно (`exit code 0`).
        
    - `failed` — команда завершилась с ошибкой (`exit code != 0`), конвейер остановлен.
        
    - `skipped` — задача пропущена (например, `build_app` не запускается при падении `test_app`).
        
    - `pending` — задача ждёт свободный Runner.
        

### 4. Краткие ответы на контрольные вопросы

1. **Что такое Continuous Integration?** Автоматическая проверка каждого коммита в репозитории (тестирование и сборка) для раннего обнаружения ошибок.
    
2. **Что такое pipeline, stage и job?** Pipeline — весь процесс проверки коммита; stage — логический этап (`test`, `build`); job — конкретная задача внутри этапа, которую запускает Runner.
    
3. **Что делает Runner?** Получает job, поднимает окружение, выполняет команды из сценария и возвращает в систему статусы, логи и артефакты.
    
4. **Где хранится описание pipeline?** В YAML-файле в самом репозитории: `.gitlab-ci.yml` (в GitLab) или `.github/workflows/ci.yml` (в GitHub Actions).
    
5. **Что означает `image: node:20-alpine`?** Указывает раннеру запускать задачи в Docker-контейнере на базе Alpine Linux с установленным Node.js 20 (в GitHub Actions мы использовали `runs-on: ubuntu-latest` + `actions/setup-node@v4` с `node-version: "20"`).
    
6. **Почему `test` и `build` оформлены отдельными jobs?** Чтобы отделить проверку кода от упаковки, сразу видеть этап возникновения ошибки и не тратить ресурсы на сборку при провале тестов.
    
7. **Что означает `exit code 0`?** Консольная команда или тестовый скрипт завершились штатно и без ошибок.
    
8. **Почему ненулевой `exit code` делает job красным?** Код возврата `!= 0` (например, `1` при ошибке `assert`) сигнализирует об аварийном завершении команды, поэтому Runner прерывает шаг и ставит статус `failed`.
    
9. **Что такое artifact и чем он отличается от исходного кода в Git?** Артефакт — это сгенерированный результат сборки (`dist/`), который временно хранится на сервере CI, а не фиксируется в истории коммитов Git.
    
10. **Что произойдёт с `build` job, если `test` stage завершился ошибкой?** Сборка не запустится и получит статус `skipped` (в GitHub Actions это обеспечивается связкой `needs: test_app`), а дефектный артефакт не создастся.
    
11. **Почему CI должен запускаться после изменения в репозитории?** Для быстрой обратной связи (fast feedback) — ошибка выявляется сразу после коммита, до публикации сборки.
    
12. **Чем локальный `npm test` отличается от запуска теста в CI?** Локальный запуск зависит от настроек и пакетов на ПК разработчика, а CI всегда запускает тесты в чистом, изолированном и воспроизводимом окружении.
    
13. **Что такое переменная `$CI_COMMIT_SHORT_SHA`?** Встроенная переменная среды с коротким хэшем текущего коммита для уникального именования артефакта (в GitHub Actions аналог — `${{ github.sha }}`).
    
14. **Где смотреть подробную причину `failed` job?** В журнале выполнения (Job Log) упавшей задачи в веб-интерфейсе CI.
    
15. **Почему намеренно сломанный тест полезен для проверки pipeline?** Он доказывает, что конвейер реально контролирует качество кода, переходит в `failed` при ошибке и блокирует сборку артефакта.

### 2. Зачем нужен каждый сервис в стенде

Все 5 контейнеров работают в изолированной сети Docker (`labnet`), а их порты опубликованы только на `127.0.0.1` (для безопасности, чтобы стенд был доступен только локально с ПК):

| Сервис (порт на ПК) | Для чего нужен |
| --- | --- |
| **Nginx / `app**` (`18080`) | Сам учебный веб-сервис: отдаёт HTML-страницы (`index.html`, `health.html`), имеет встроенный `healthcheck` и пишет логи доступа.

 |
| **Blackbox Exporter** (`19115`) | Внешний «зонд»: по запросу Prometheus отправляет HTTP GET-запрос к `app` и переводит ответ (200 OK или сбой) в формат метрик Prometheus.

 |
| **Prometheus** (`19090`) | Система сбора метрик: каждые 5 секунд опрашивает Blackbox Exporter, хранит историю в базе (TSDB) и проверяет правило тревоги `alerts.yml`.

 |
| **Alertmanager** (`19093`) | Диспетчер оповещений: принимает сработавшие тревоги от Prometheus, группирует их и убирает дублирующиеся срабатывания.

 |
| **Grafana** (`13000`) | Система визуализации: подключается к Prometheus и отображает на дашборде график доступности сервиса (`probe_success`).

 |

**Цепочка работы:** `Prometheus` $\rightarrow$ опрашивает `Blackbox Exporter` $\rightarrow$ который стучится в `Nginx (app)`. Если сервис упал, `Prometheus` отправляет тревогу в `Alertmanager`, а `Grafana` рисует падение графика.

### 3. Основные определения и понятия

* **Infrastructure as Code (IaC — инфраструктура как код):** подход, при котором серверы, сети и контейнеры описываются не ручными командами, а в виде декларативных конфигурационных файлов (`compose.yaml`, `prometheus.yml`), которые хранятся в Git. Это даёт воспроизводимость и историю изменений.


* **Отличие Docker Compose от Bash-скрипта:** `compose.yaml` **декларативен** (описывает *что* должно работать в итоге), а `deploy.sh` **императивен** (описывает *пошаговый алгоритм* проверок и команд).


* **Идемпотентность:** свойство операции, при котором повторный запуск с теми же настройками оставляет систему в прежнем состоянии без дубликатов и пересоздания контейнеров.


* **Метрика `probe_success` и метка `instance`:** `probe_success` показывает результат внешней HTTP-проверки (`1` — сайт доступен, `0` — недоступен), а `instance` хранит проверяемый URL (`http://app:80/` и `http://app:80/health.html`).


* **Статусы тревоги `pending` и `firing` (и зачем `for: 20s`):**
* `pending` — условие сбоя (`probe_success == 0`) уже выполнилось, но ещё не прошло время удержания.


* `firing` — сбой длится дольше 20 секунд (`for: 20s`), тревога подтверждена и отправлена в Alertmanager. Задержка `20s` нужна, чтобы не поднимать ложную панику из-за случайной разовой задержки сети.




* **Разница между Docker `healthcheck` и Blackbox Exporter:** Docker `healthcheck` проверяет контейнер *изнутри* (жив ли сам процесс Nginx), а Blackbox Exporter проверяет сервис *снаружи по сети* (как реальный пользователь) и отдаёт метрики в Prometheus.

### 4. Использованные команды и что они значат

* **Проверка и валидация:**
* `bash -n deploy.sh` — проверяет Bash-скрипт на синтаксические ошибки без его запуска.


* `docker compose config -q` — проверяет синтаксис `compose.yaml` и подстановку переменных из `.env` без создания контейнеров (`-q` выводит сообщения только при ошибке).




* **Развёртывание и защита скрипта (`deploy.sh`):**
* `chmod u+x deploy.sh` и `./deploy.sh` — выдаёт право на выполнение и запускает сценарий.


* `set -Eeuo pipefail` — останавливает скрипт при любой ошибке команды (`-e`), пустой переменной (`-u`) или сбое в конвейере (`pipefail`).


* `trap '...' ERR` — перехватывает сбой и выводит номер строки (`$LINENO`), на которой упал скрипт.


* `docker compose up -d` — запускает все контейнеры стека в фоновом режиме (`-d`).




* **Диагностика и доказательство идемпотентности:**
* `docker compose ps` (и `ps -q app`) — показывает состояние контейнеров (`Up`, `healthy`, `Exited`); ключ `-q` выводит только ID контейнера `app`.


* `docker inspect -f '{{.State.StartedAt}}' <ID>` — достаёт из метаданных контейнера точное время его запуска (чтобы доказать, что при повторном `./deploy.sh` контейнер не перезапускался).


* `docker compose logs --tail=30 app` — выводит последние 30 строк логов контейнера `app` для поиска причины сбоя.


* `curl -fsS [http://127.0.0.1:18080/](http://127.0.0.1:18080/)` — отправляет HTTP-запрос к веб-серверу (`-f` считает коды ошибок 4xx/5xx сбоем, `-sS` скрывает прогресс-бар, но показывает текст ошибки).




* **Управление сервисами и Git:**
* `docker compose restart prometheus` — перезапускает только контейнер Prometheus, чтобы он перечитал обновлённый `prometheus.yml`.


* `docker compose stop app` / `docker compose start app` — останавливает и снова запускает только веб-сервер для моделирования инцидента.


* `git init`, `git add`, `git status`, `git commit`, `git log --oneline` — создание локального репозитория, проверка отсутствия `.env` в индексе и фиксация версий конфигурации.


* `docker compose down` — останавливает и удаляет контейнеры и сеть `labnet` после работы (без флага `-v`, чтобы не стереть том `grafana_data`).

### 5. Короткие ответы на частые вопросы при защите

* **Почему в Grafana мы указали `http://prometheus:9090`, а не `localhost:19090`?**
Потому что внутри контейнера Grafana адрес `localhost` указывает на саму Grafana. По имени сервиса `prometheus` и внутреннему порту `9090` контейнеры общаются друг с другом через встроенный DNS Docker в общей сети `labnet`.


* **Почему `depends_on` само по себе не гарантирует готовность приложения?**
`depends_on` задаёт только порядок *запуска* контейнеров, но не ждёт, пока программа внутри полностью инициализируется и начнёт принимать запросы. Для проверки реальной готовности нужен `healthcheck` и цикл проверки `curl` в `deploy.sh`.


* **Почему при имитации аварии нельзя останавливать Prometheus или Blackbox Exporter?**
Если остановить систему мониторинга, мы потеряем наблюдаемость и не сможем отличить падение самого веб-приложения от падения системы проверки.


* **Почему `.env` нельзя загружать в Git?**
В `.env` хранится реальный пароль администратора Grafana (`GRAFANA_PASSWORD`); в репозиторий загружается только безопасный шаблон `.env.example`.
