# Подготовка к защите ЛР №4: ООП, Декораторы и Middleware

## 1. Что мы делали (Обязательная часть)

Мы реализовали систему управления финансовыми инструментами и сквозную функциональность на двух языках, чтобы сравнить подходы к ООП и аспектно-ориентированному программированию.

### Python
*   **Иерархия классов (`instruments.py`):** Создали абстрактный базовый класс `FinancialInstrument` с магическими методами (`__str__`, `__eq__`). Реализовали наследников `Stock`, `Bond`, `Option` с разной логикой расчёта стоимости. Класс `Portfolio` поддерживает сложение через `__add__` и подсчёт элементов через `__len__`.
*   **Декораторы (`decorators.py`):** Написали три декоратора для добавления поведения без изменения бизнес-логики:
    *   `@timing`: замеряет время выполнения через `time.perf_counter()`.
    *   `@log`: выводит аргументы вызова функции.
    *   `@cache`: сохраняет результаты в словаре для повторных вызовов с теми же аргументами.
*   **Middleware (`middleware.py`):** Реализовали паттерн «цепочка ответственности» для обработки заказов. Функции `logging_middleware` и `tax_middleware` оборачивают обработчик, добавляя логирование и налог 20%. Функция `apply_middlewares` собирает их в пайплайн в обратном порядке.

### Go
*   **Структуры и интерфейсы (`instruments.go`):** Вместо классов использовали структуры (`struct`) и встраивание (`embedding`) `BaseInstrument`. Интерфейс `FinancialInstrument` реализуется неявно: любая структура с методами `Value()` и `Ticker()` ему удовлетворяет. Портфель хранит срез интерфейсов `[]FinancialInstrument`.
*   **Middleware (`middleware.go`):** Тип `Handler` — это функция `func(Order) Order`. Middleware принимают `Handler` и возвращают новый `Handler`. Цепочка собирается функцией `ApplyMiddlewares`, которая применяет обёртки от последней к первой, обеспечивая правильный порядок выполнения.

## 2. Бонусные задания

Бонусы демонстрируют продвинутые техники: фабрики декораторов, восстановление после сбоев и анализ производительности.

*   **Python: Декоратор с параметрами `@repeat(n)`**
    Это **фабрика декораторов**. Функция `repeat` принимает число `n` и возвращает сам декоратор. При применении `@repeat(3)` сначала вызывается `repeat(3)`, который возвращает функцию-декоратор, и только она оборачивает целевую функцию. Внутри обёртки цикл вызывает исходную функцию ровно `n` раз.
*   **Go: PanicMiddleware**
    Использует конструкцию `defer` + `recover()` для перехвата паник. Если внутри обработчика происходит `panic`, middleware ловит её, логирует ошибку и возвращает безопасный `Order{Amount: 0}`, предотвращая падение всего приложения. Это аналог try-catch в других языках.
*   **Бенчмарк**
    Замерили скорость обработки 1 млн операций. Go оказался быстрее Python примерно в 18–20 раз благодаря компиляции в машинный код, статической типизации и отсутствию накладных расходов интерпретатора (GIL, динамическая диспетчеризация методов).

## 3. Ответы на контрольные вопросы (из методички)

1.  **Что такое абстрактный класс? Зачем он нужен?**
    Абстрактный класс (ABC) — это шаблон, который нельзя инстанциировать напрямую. Он нужен для определения общего интерфейса и принудительной реализации ключевых методов (например, `value()`) во всех наследниках, гарантируя единообразие API.
2.  **Как в Python работает `__eq__`? Что будет, если его не реализовать?**
    `__eq__` определяет логику оператора `==`. По умолчанию Python сравнивает объекты по идентичности (адресу в памяти). Без переопределения два разных объекта с одинаковыми данными будут считаться неравными.
3.  **Зачем нужен `@functools.wraps` в декораторах?**
    Он копирует метаданные оригинальной функции (`__name__`, `__doc__`, аннотации) в обёртку. Без него отладка становится сложнее, так как все декорированные функции будут называться `wrapper`, а их docstring пропадёт.
4.  **Как работает декоратор `@cache`? Где хранится кэш?**
    Кэш хранится в словаре `memo`, объявленном в замыкании декоратора (вне `wrapper`, но внутри `cache`). Ключом является кортеж из позиционных и именованных аргументов. При повторном вызове с тем же ключом результат берётся из словаря, а функция не выполняется.
5.  **В чём отличие наследования в Python от встраивания (embedding) в Go?**
    Наследование в Python создаёт отношение «is-a» и передаёт методы через MRO. Встраивание в Go — это композиция («has-a»), где методы встроенной структуры просто «продвигаются» на уровень внешней. В Go нет полиморфизма через встраивание, только через интерфейсы.
6.  **Как в Go работает неявная реализация интерфейсов?**
    Структура удовлетворяет интерфейсу автоматически, если у неё есть все требуемые методы. Не нужно писать ключевое слово `implements`. Это проверяется на этапе компиляции и обеспечивает слабую связность.
7.  **Что такое middleware? Как реализуется цепочка middleware в Go?**
    Middleware — это функция, оборачивающая обработчик и добавляющая поведение до/после него. Цепочка реализуется путём последовательного применения функций-обёрток: каждая следующая middleware принимает результат предыдущей, формируя вложенную структуру вызовов.
8.  **Почему `ApplyMiddlewares` применяет функции в обратном порядке?**
    Чтобы первый middleware в списке аргументов оказался самым внешним слоем (вызывался первым). При прямом порядке последний middleware стал бы внешним, что нарушило бы ожидаемую логику (например, логирование должно видеть исходный запрос, а не уже изменённый налогом).
9.  **Чем `__add__` в Python отличается от обычного метода `add`?**
    `__add__` позволяет использовать оператор `+` для пользовательских объектов, делая код более читаемым и «pythonic». Обычный метод требует явного вызова `obj.add(other)`, что менее естественно для арифметических операций.
10. **Почему в Go `Portfolio.Add` принимает указатель `(*Portfolio)`, а `Stock.Value` — значение?**
    `Add` модифицирует состояние портфеля (добавляет элемент в срез), поэтому нужен указатель для изменения оригинала. `Value` только читает данные и не меняет объект, поэтому передача по значению безопаснее и эффективнее для небольших структур.

## 4. Самое важное из лекции (Ключевые выводы)

*   **Философия ООП:** Python делает ставку на гибкость, магию (dunder-методы) и наследование. Go выбирает простоту, явность и композицию. Оба подхода решают одни задачи, но разными путями.
*   **Сквозная функциональность (Cross-cutting concerns):** Логирование, тайминг, кэширование и аутентификация затрагивают многие модули. Их нельзя смешивать с бизнес-логикой.
*   **Инструменты разделения ответственности:**
    *   В Python это **декораторы** (универсальны, работают с любыми функциями).
    *   В Go это **middleware** (специфичны для HTTP/обработчиков) и **декораторы интерфейсов**.
*   **Критические правила:**
    *   Всегда используйте `@functools.wraps` в Python.
    *   В Go middleware должны вызывать `next.ServeHTTP`, иначе цепочка прервётся.
    *   Для обработки паник в Go обязательно используйте `defer recover()`.
    *   Не создавайте слишком много слоёв (более 5–7) — это усложняет отладку.
*   **AOP (Аспектно-ориентированное программирование):** Декораторы и middleware — это практическая реализация AOP. Они позволяют добавлять аспекты (поведение) декларативно, сохраняя чистоту основного кода.
